# 문서 본문 통째 저장

문서 본문을 줄마다 `POST/PATCH/DELETE /block`으로 저장하면 길어질수록 느려집니다. 서버가 블록 하나를 저장할 때마다 문서 전체를 다시 읽기 때문입니다. 이제 본문을 트리째 한 번에 보내면, 서버가 `id`를 기준으로 바뀐 블록만 반영합니다. 레코드의 `PATCH /record/{id}` `blocks`도 같은 방식입니다. 블록 모양은 [workspace_page_frontend.md](workspace_page_frontend.md), 실시간 반영은 [workspace_collab_frontend.md](workspace_collab_frontend.md)입니다. 기본 경로는 `/api/v1/workspace`이고 인증은 JWT입니다.

## 유저 플로우

1. 문서를 열 때 `GET /page/{page_id}`(레코드는 `GET /record/{id}`)로 `blocks`와 `collab_seq`를 받습니다.
2. 사용자가 글을 고치는 동안은 화면의 트리만 바꾸고 서버에 보내지 않습니다.
3. 입력이 1~2초 멈추면, 포커스를 잃으면, 페이지를 떠나기 직전에 본문 전체 트리를 보냅니다.
4. 응답의 `ids`로 새 블록에 `id`를 붙이고, `seq`를 다음 저장의 `base_seq`로 씁니다.
5. 409가 오면 다른 사람이 먼저 고친 것입니다. 문서를 다시 불러와 합친 뒤 다시 저장합니다.

## 문서 페이지 저장

`PUT /page/{page_id}/block`

```json
{
  "base_seq": 12,
  "blocks": [
    {"id": 101, "type": "paragraph", "content": {"text": "그대로"}},
    {"type": "paragraph", "content": {"text": "새로 끼운 줄"}},
    {
      "id": 102,
      "type": "toggle",
      "content": {"text": "토글"},
      "children": [{"id": 103, "type": "paragraph", "content": {"text": "자식"}}]
    }
  ]
}
```

- 트리 모양은 레코드 생성의 `blocks`와 같습니다. 자식은 `children`에 넣습니다.
- `id`가 있으면 기존 블록입니다. 내용, 타입, 부모, 순서 중 달라진 것만 고칩니다. 같으면 건드리지 않습니다.
- `id`가 없으면 새 블록입니다.
- 서버에 있는데 트리에 없는 블록은 지웁니다. 그 블록의 자식도 지워집니다.
- 순서는 배열 순서입니다. `position`을 보내도 무시합니다.
- `id`는 이 문서의 블록이어야 합니다. 다른 문서의 블록이거나 같은 `id`가 두 번 있으면 400입니다. 표 행, 표 칸, 단의 부모 규칙과 `content` 검증은 기존과 같고, 어긋나면 400이며 아무것도 저장하지 않습니다.
- 문서 페이지가 아니면 400, `access`가 `admin`인데 멤버가 보내면 403입니다.

응답입니다. 바뀐 블록만 옵니다. 문서 전체를 다시 돌려주지 않습니다.

```json
{
  "seq": 13,
  "ids": [101, 205, 102, 103],
  "blocks": [
    {"id": 205, "page_id": 7, "record_id": null, "parent_id": null, "type": "paragraph",
     "content": {"text": "새로 끼운 줄"}, "position": 512,
     "created_at": "2026-11-09T13:00:00", "updated_at": "2026-11-09T13:00:00"}
  ],
  "deleted_ids": []
}
```

- `ids`는 요청 트리를 위에서 아래로, 부모 다음에 자식 순서로 훑었을 때의 블록 id입니다. 요청에서 같은 순서로 훑으면서 `id`가 없던 블록에 차례로 붙입니다.
- `blocks`는 새로 만들거나 바뀐 블록입니다. 서버가 정한 `position`을 화면 상태에 반영합니다.
- `deleted_ids`는 지워진 블록입니다.
- 바뀐 것이 없으면 `blocks`와 `deleted_ids`가 비고 `seq`도 그대로입니다.

## 레코드 저장

`PATCH /record/{record_id}`의 `blocks`에 `id`를 넣으면 같은 방식으로 반영합니다. `base_seq`도 보낼 수 있습니다. 응답은 기존처럼 상세 레코드이고, `blocks`와 `collab_seq`가 있습니다.

```json
{"blocks": [{"id": 9, "type": "paragraph", "content": {"text": "고침"}}], "base_seq": 4}
```

`id`를 하나도 보내지 않으면 지금까지처럼 본문을 통째로 바꿉니다. 이때는 블록 id가 모두 새로 생기므로 댓글과 멘션 위치도 이어지지 않습니다. 레코드 생성의 `blocks`는 그대로입니다.

## 충돌

`base_seq`는 `GET` 응답의 `collab_seq`나 직전 저장의 `seq`입니다. 보내면 서버의 현재 번호와 같을 때만 저장하고, 다르면 409입니다. 409이면 아무것도 저장하지 않습니다.

`base_seq`를 빼면 확인하지 않습니다. 이때 다른 사람이 그 사이에 추가한 블록은 내 트리에 없으므로 지워집니다. 사람이 편집하는 화면은 항상 보내세요.

번호는 변경 한 번마다 올라갑니다. 문서방 소켓을 쓰는 화면은 다른 사람의 `collab`을 받을 때마다 화면 트리에 반영하고 그 `seq`를 `base_seq`로 이어 가야 합니다. 반영하지 않으면 저장할 때마다 409가 납니다. 내가 보낸 저장으로 생긴 `collab`은 `seq`가 응답의 `seq` 이하이므로 건너뜁니다.

## 문서방 알림

저장 한 번에 바뀐 블록마다 `collab`이 옵니다. `deleted`, `created`, `updated` 순입니다. 바뀐 블록이 30개를 넘거나 기존 블록을 하나도 남기지 않고 바꾼 경우에는 `reload` 하나만 옵니다. `reload`를 받으면 문서를 다시 조회합니다. 워크스페이스 소켓에는 문서 페이지는 `page`, 레코드는 `record`의 `updated`가 한 번 옵니다.

## `position`

값이 연속이 아닙니다. 중간에 끼운 블록은 이웃 사이 값을 받고, 서버가 필요할 때만 형제 전체를 `1024` 간격으로 다시 매깁니다. 정렬에만 쓰고, 배열 인덱스라고 가정하지 마세요. 정렬은 `position`, `id` 순입니다.

## 개정과 알림이 달라진 점

- 같은 사용자가 5분 안에 다시 고치면 새 개정을 만들지 않습니다. 그 편집 세션을 시작하기 직전 본문이 이미 개정에 있습니다. 다른 사용자가 고치거나 5분이 지나면 새 개정이 생깁니다. 개정 복원은 항상 직전 본문을 개정으로 남깁니다.
- 사용자 멘션 알림은 바뀐 블록에 새 멘션이 있을 때만 갑니다. 한 문서에서 이미 멘션된 사람은 다시 알리지 않는 규칙은 같습니다.

## 구현 체크리스트

- 줄마다 요청하지 않는다. 입력 후 1~2초 debounce, 포커스 아웃, 이탈 직전에 보낸다.
- 요청은 한 번에 하나만 보낸다. 저장 중에 쌓인 변경은 모아서 응답이 온 뒤 다음 요청에 보낸다.
- 새 블록에는 `id`를 넣지 않는다. 저장 응답의 `ids`로 채운다.
- 항상 `base_seq`를 보내고, 응답 `seq`와 다른 사람의 `collab.seq`로 갱신한다.
- 409이면 문서를 다시 불러오고 내가 고친 내용을 합쳐 다시 보낸다.
- 응답 `blocks`의 `position`을 화면 상태에 반영한다.
- 지운 블록은 트리에서 빼면 된다. 따로 삭제 요청을 보내지 않는다.
- 이탈 직전 저장은 `fetch`의 `keepalive: true`로 보낸다. 이 방식은 본문이 64KB를 넘으면 브라우저가 거절하므로, 큰 문서는 평소 debounce 저장에 맡기고 이탈 직전에는 못 보낸 변경만 시도한다.

## 비범위

- 글자 단위 병합. 같은 블록을 두 사람이 고치면 나중에 저장한 내용이 남습니다.
- 바뀐 블록만 보내는 방식(ops 배열). 필요하면 이 API 뒤에 더합니다.
- 기존 `POST/PATCH/DELETE /block`은 그대로 있습니다. 단건 호출이 필요한 곳(MCP, 문서방 `op`)에서 씁니다.
